Story Network Plan

How Versatile should build the map of who, where and what happens in a book, so it keeps growing as the book grows and can still be read by volume, chapter, scene and moment in time. It answers one question first: should we switch to GLiNER and a GLiNER-style relation model?

§0The plan in one sentence

Keep one model call per scene as the reader, store everything it learns as small dated facts that point back to the exact scene and sentence, run every name through one shared "who is this?" step, and treat volumes as a way of looking at the facts, not a place where facts live.

§0.5Words used in this plan

These words come up again and again. Each one in plain English:

Entity
A thing the story is about: a person, a place, an object, a group, an event.
Mention
One place in the text where an entity shows up: "Alaric", "the old king", "he".
Alias
Another name for the same entity. "The old king" is an alias of Alaric.
Coreference
Working out which mentions point to the same entity. The hard version includes "he" and "she".
Relation
A link between two entities: Alaric trusts Mira.
Claim
One small fact the book states, with where it came from and when it is true. "Alaric trusts Mira, from chapter 2, scene 3, until chapter 9."
Provenance
Where a claim came from: which scene, which sentence, which tool.
F1
One score for "did it find the right things". 100 is perfect. 50 means it gets about half right. It mixes two questions: how much of what it found is right, and how much of what is there it found.
Zero-shot
Using a model on a task it was never trained on, by just telling it the labels. Cheap to start, usually much weaker.
Gold set
A small set of answers a person wrote by hand. We measure every tool against it.

§2What exists today

Versatile already builds a story network. Here is how, in order.

  • Reading. bookAnalysis.ts asks qwen3:8b for named people (with role and description), places, up to 5 key facts and up to 5 relations per scene. Generated scenes get the same kind of call in useStoryWriter.ts.
  • "Who is this?" Only on import (resolveNames): a short name joins the one longer name that contains it, with checks on titles and gender. If a name could be two people, the model votes and the app merges only when it is 60% sure. Generated scenes match names exactly, so "Ilse" and "Ilse Varn" can become two people. Nobody handles "he" or "the old king".
  • Relations. One global table, graphEdges. Each edge has a type, a volume, and "valid from" and "valid until" chapters. A new relation that clashes with an open one ends the old one (edgeTimeline.ts). Edges know their chapter, not their scene.
  • Change over time. entityStates keeps one row per person per scene: present, alive, where, what they know. It is filled by regex over the key facts.
  • Volumes. Already a filter on one global network (db-volume-entities.ts), not separate networks.
  • Contradictions. The critic compares a scene with a ledger of earlier facts. The Beta Reader runs fixed rules over entityStates, then asks the model about suspicious pairs.
  • Cost. About one minute per scene. Ethan Frome: 35k words, 12 scenes, 10.8 minutes. The Time Machine: 16.2 minutes, 12 people, 22 places, 23 links.
Gaps found while mapping this
  • The two paths (import and generation) do not share the "who is this?" step.
  • Relations remember the chapter, not the scene or the sentence. You cannot click a link and see the line that proves it.
  • The server copy of an edge (GraphEdge.cs) has no "valid from / until" fields. A sync drops the dates.
  • Only three entity kinds have tables: characters, locations, plot threads. Objects exist only inside entityStates. Groups, events and ideas have nowhere to live.

§2.5The question: GLiNER + GLiDRE?

The idea was: GLiNER finds the entities, a GLiNER-style model finds the relations, code joins and cleans them into one network, and volumes are cut from the network afterwards. First, a naming check. There is no model called "GLiDER". The closest ones are GLiDRE (relations across a whole document, 2025), GLiREL (relations, 2025) and GLiNER-Relex (entities and relations together, May 2026). This plan judges those.

§3Locked decisions

  • D1One model call per scene stays the main reader. It is the only option here that can say "she betrays him" when the text only shows it, and its summary and facts are needed anyway.
  • D2No GLiDRE or GLiREL now. Zero-shot they score about 17 F1 even when handed the answers to the hard part. They also need a Python server, which a local-first browser app does not have.
  • D3Everything becomes a claim. Relations, states and key facts are all the same shape: who, what, whom or value, from when, until when, which scene, which sentence, which tool.
  • D4Volumes, chapters and scenes are views. A claim stores its scene. Its chapter and volume are looked up, never written onto it.
  • D5One "who is this?" step for imported and generated text.
  • D6No full pronoun resolution. The reading call already settles "he" inside a scene. Across scenes we match names and descriptions, which is the part that breaks today.
  • D7A one-at-a-time fact changes only with evidence. No evidence means a flag, not an overwrite.
  • D8Measure before building. The gold set comes first. GLiNER ships only if it passes G7.

§5Build order

  1. S0Gold set and scorer2–3 days, mostly labelling
    What
    Hand-label both books: every person and place, every alias ("Zeena" = "Mrs. Frome"), relations from a fixed list of about 20 types, and every change (who leaves, who dies, who stops trusting whom). Write a script that scores any pipeline against it.
    Why
    The papers measured Wikipedia, not novels. Our own decisions need our own numbers.
    Done when
    G1: today's pipeline has a published score per type.
  2. S1Claims store and migration3–4 days
    What
    New Dexie table claims (new schema version, migration handler, changelog entry). Copy every edge, entity state and key fact into it. Add an aliases table and entity kinds for objects, groups, events and ideas. Add the missing date fields to the server's GraphEdge and sync.
    Why
    One shape means one set of checks and one set of views.
    Done when
    G2: counts match, the sync round trip keeps dates, old screens still read the same data.
  3. S2One "who is this?" step2–3 days
    What
    Move resolveNames, resolvePlaces and the model vote into one service. Use it in import and in the sync after generation. Add the rule for descriptions such as "the old king".
    Done when
    G3: no second "Ilse", alias score on the gold set at least as good as today.
  4. S3Reader v2: a quote for every fact2–3 days + one live run
    What
    Change the scene-reading JSON so every relation and fact carries a short quote, and every claim is written with its scene. Code checks each quote, the way the critic's quotes are already checked.
    Watch
    A bigger answer makes each call slower. G8 caps the cost at +20%.
    Done when
    G4 and G8 pass on both books.
  5. S4Change versus contradiction2 days
    What
    A short list of one-at-a-time predicates. A clash closes the old claim only if the new scene shows the change. Otherwise it is flagged where the writer already sees warnings.
    Done when
    G5 on the gold changes, plus tests for "dies", "moves", "marries", "stops trusting".
  6. S5Views and the network panel3 days
    What
    Four queries: by volume, chapter, scene, and "true at scene N". Point the network panel, the writer's context and the checks at them. Clicking a link shows its quote.
    Done when
    G6: moving a chapter between volumes changes the volume views with no claim rewritten.
  7. S6GLiNER experiment2 days, in parallel
    What
    Run GLiNER in the browser (the gliner npm package, ONNX) over both books. Compare its names with the reader's names against the gold set.
    Done when
    G7 passes and it ships as a checker, or it fails and the report says why. Either outcome is a result.
  8. S7Later: a small relation model of our ownbacklog
    What
    Once thousands of scenes carry quoted relations from S3, use them to train a GLiNER-style relation model on story relations. This is how GLiDRE built its own training data (from an LLM).
    Why later
    Only a trained model beats the zero-shot 17 F1, and we have no training data until S3 has run for a while.

§7Decided and open

Decided

  • LLM reader stays (D1). No GLiDRE or GLiREL now (D2).
  • One claims store, volumes as views, one resolver (D3 to D5).
  • Measure first. GLiNER must pass a gate (D8).

Open

  • Relation list. Which 20 or so relation types go in the gold set? A starting list: knows, trusts, distrusts, loves, family_of, married_to, works_for, owns, located_at, travels_to, fights, betrays, protects, member_of, before, after.
  • Story time versus reading order. Flashbacks put events out of order. This plan dates claims by reading order. Do we also need "story time"? Only if the gold set shows flashbacks breaking the checks.
  • Who labels. You, or the same reviewer setup used for the 78-scene judge labels?
  • Writer flags. Where do "did you mean it?" flags show: the existing review list, or the network panel?

§8Backlog

  • S7, a small relation model trained on our own quoted relations.
  • Full pronoun coreference across scenes, if the gold set shows it matters.
  • Story-time dating for flashbacks.
  • A merge and split screen for entities ("these two are the same person").
